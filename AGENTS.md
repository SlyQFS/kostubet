# 🤖 AGENTS.md — Руководство для AI-агентов и разработчиков

Данный документ содержит полное описание архитектуры, структуры файлов, ключевых соглашений, правил разработки и механизмов расширения кодовой базы **Kostubet GitHub & APK Watcher Telegram Bot**.

---

## 📌 1. Обзор проекта и стек технологий

**Kostubet GitHub & APK Watcher** — это высокопроизводительный асинхронный Telegram-бот на **Rust**, решающий следующие задачи:
1. **Фоновое отслеживание GitHub-репозиториев**: проверка новых релизов, пре-релизов (включая nightly-сборки) и коммитов через GitHub REST API с поддержкой ETag-кэширования (без слепых тегов).
2. **Публикация релизных карточек**: формирование красивых карточек в HTML с обложками, тегами, описанием, списком изменений (changelog) и кнопками скачивания в каналы и форумные топики супергрупп (`message_thread_id`).
3. **Каталог кастомных приложений и модулей**: загрузка APK, Magisk/KSU модулей (`.zip`) и архивов (`.7z`) через Telegram-бот, автоопределение архитектур (`arm64-v8a`, `armeabi-v7a`, `universal`, `x86_64`, `x86`) и архивов (`archive`), версионирование и прямая доставка файлов пользователям по `file_id`.
4. **Указание автора предложения / публикации**: автоматическое сохранение Telegram-юзернейма автора (`@username`) для GitHub-предложений и загруженных приложений с отображением в карточках релизов (`👤 Предложил: @username`) и админ-панели.
5. **Двухуровневая модерация**: интерактивная проверка заявок на отслеживание репозиториев и публикацию приложений/модулей администраторами.
6. **Персистентный FSM в SQLite**: пошаговые диалоги подачи заявок и редактирования сохраняются в базе данных и переживают перезапуск бота.

### Ключевой стек
- **Язык**: Rust (Edition 2021)
- **Асинхронный runtime**: `tokio` (multi-thread)
- **Telegram Framework**: `teloxide` 0.14 (`dptree`, `macros`, `ctrlc_handler`, `rustls`)
- **База данных**: SQLite через `sqlx` (режим WAL, connection pool, асинхронный драйвер `runtime-tokio-rustls`)
- **HTTP клиент**: `reqwest` (rustls-tls, json)
- **Логирование / Трейсинг**: `tracing`, `tracing-subscriber` (EnvFilter)
- **Утилиты**: `serde`, `serde_json`, `toml`, `anyhow`, `html-escape`, `dotenvy`

## 🏗 3. Архитектурные принципы и ключевые механизмы

### 3.1. Диспетчеризация через Teloxide `dptree`
В `src/main.rs` строится дерево обработки `dptree`, разделенное на две основные ветви:
1. **`Update::filter_message()`**:
   - `filter_command::<Command>()` -> отправляет команды в `handlers::handle_command`.
   - Ветвления по FSM-состояниям (`SubmitApk`, `EditApk`, `Admin`, `Suggest`) -> направляют текстовые сообщения и документы в соответствующие обработчики диалогов.
2. **`Update::filter_callback_query()`**:
   - Направляет все нажатия инлайн-кнопок в `handlers::callbacks::handle_callback`.

> ⚠️ **Правило приватности ЛС**: Все интерактивные команды и диалоги разрешены **только в приватном чате с ботом** (`msg.chat.is_private()`). Если пользователь вызывает команду в группе, бот отправляет уведомление `GROUP_NOTICE_HTML` и прерывает обработку.

### 3.2. Персистентный FSM в SQLite (`SqliteDialogueStorage`) и UX диалогов
- Состояние диалога каждого пользователя сериализуется в JSON и сохраняется в таблице `dialogue_state` (`chat_id`, `state_json`, `updated_at`).
- При перезапуске бота диалоги пользователей не сбрасываются.
- При завершении диалога или вызове `/cancel` обязательно вызывается `dialogue.exit().await` (или переводится в `DialogueState::Idle`).
- **Инлайн-кнопки на каждом шаге диалогов**: Все интерактивные шаги в `/suggest` и `/submitapk` снабжаются инлайн-кнопками `[ ⏩ Пропустить ]` и `[ ❌ Отменить ]` (`skip_or_cancel_keyboard()`) или `[ ❌ Отменить ]` (`cancel_keyboard()`). Обработка нажатий синхронизирована через коллбэки `submit_skip`, `submit_confirm:cancel`, `sugg_skip`, `sugg_cancel`.
- **Лаконичные тексты и плейсхолдеры**: В диалогах и подсказках используются простые и короткие формулировки на русском языке, а в качестве универсальных примеров — нейтральные плейсхолдеры `example`, `#example`, `https://github.com/owner/example`.

### 3.3. База данных: SQLite + WAL Mode
- Подключение настраивается в `src/db/mod.rs` с параметрами:
  - `journal_mode(SqliteJournalMode::Wal)` — параллельное чтение воркером поллера и запись пользователями без взаимных блокировок.
  - `busy_timeout(Duration::from_secs(5))` — ожидание освобождения блокировок.
  - `foreign_keys(true)` — контроль целостности связей.
- Инициализация схемы и миграции выполняются идемпотентно в методе `Database::init_schema()` с помощью `CREATE TABLE IF NOT EXISTS` и `CREATE INDEX IF NOT EXISTS`.
- Доступ к таблицам инкапсулирован в паттерне **Repository**: `db.admins()`, `db.tools()`, `db.tags()`, `db.suggestions()`, `db.custom_apps()`, `db.audit()`.

### 3.4. Telegram API: Лимиты, Карточки и Отправка Файлов
- **Лимиты длины сообщений**:
  - Подпись к фото (`caption`): **максимум 1024 символа**.
  - Текстовое сообщение: **максимум 4096 символов**.
- **Разбиение сообщений (`render.rs`)**:
  - Если карточка содержит обложку и длинный список изменений (changelog), сначала отправляется фото с заголовком и метаданными, а полный changelog отправляется следом отдельным сообщением с `LinkPreviewOptions::disabled()`.
- **Изолированный Retry-механизм (`send_with_retry`)**:
  - При получении ошибки `RequestError::RetryAfter(secs)` бот делает паузу для конкретного запроса. Обработка локализована на уровне одного вызова, что исключает дублирование карточек/фотографий при временном rate-limit Telegram.
- **Доставка APK, модулей и архивов**:
  - Файлы отправляются через `send_document` по Telegram `file_id`.
  - Файлы не сохраняются на диск сервера бота, что экономит место и обеспечивает мгновенную отдачу.
  - Поддерживаются форматы `.apk`, `.zip` (включая Magisk/KSU/APatch модули) и `.7z` (до 2 ГБ на файл).

### 3.5. GitHub API: Оптимизация квот, Релизы и Кнопки Скачивания
- Фоновый поллер `src/poller.rs` опрашивает GitHub API с интервалом `POLL_INTERVAL_SECS`.
- Запросы отправляют заголовок `If-None-Match: <etag>`. При ответе `304 Not Modified` тело ответа не передается и квота GitHub API не расходуется.
- Глобальный клиент инициализируется в `src/services/github.rs` с опциональным `GITHUB_TOKEN` (лимит 5000 запр/час вместо 60).
- **Кнопки скачивания и приоритеты APK**:
  - Если в релизе есть `.zip` или `.7z` — формируется кнопка перехода на страницу релиза на GitHub (`⬇️ Скачать релиз`).
  - При наличии APK-файлов применяется строгий приоритет:
    1. `universal` — если есть universal APK, присылается прямая кнопка (`⬇️ Скачать (universal)`).
    2. `arm64-v8a` (v8) — если нет universal, но есть v8, присылается прямая кнопка (`⬇️ Скачать (arm64-v8a)`).
    3. `armeabi-v7a` (v7) — никогда не отправляется напрямую (ссылка на релиз).
    4. Если единственный APK без явной архитектуры — кнопка (`⬇️ Скачать (apk)`).
    5. Во всех остальных случаях (только v7, x86 и т.д.) — кнопка `⬇️ Скачать релиз`.

## 📋 4. Правила написания кода (Coding Guidelines)

При модификации существующего кода или создании новых фич AI-агенты должны строго следовать данным стандартам:

### 4.1. Безопасность HTML и форматирование сообщений
- Всегда используйте `ParseMode::Html`.
- **Любой динамический текст** (имена пользователей, названия репозиториев, коммиты, описания, теги), попадающий в HTML, **ОБЯЗАТЕЛЬНО** должен экранироваться функцией `html_escape::encode_text`:
  ```rust
  use html_escape::encode_text;
  let safe_title = encode_text(&user_input);
  let html = format!("<b>{}</b>", safe_title);
  ```

### 4.2. Обработка ошибок и логирование
- Используйте `anyhow::Result` и `anyhow::Context` для обогащения контекста ошибок:
  ```rust
  .with_context(|| format!("Не удалось загрузить данные приложения id={}", app_id))?;
  ```
- Логируйте ключевые события через макросы библиотеки `tracing`:
  ```rust
  use tracing::{info, warn, error, debug};
  info!(repo = %repo_name, "Новый релиз успешно опубликован");
  ```
- Не используйте `unwrap()` или `expect()` в обработчиках production-кода, если возможна ошибка во время выполнения (используйте оператор `?` или `match`/`if let`).

### 4.3. Асинхронность и блокирующие операции
- Кодовая база работает на Tokio. Никаких синхронных блокирующих вызовов (`std::thread::sleep`, синхронные блокирующие чтения файлов или сетевые сокеты).
- Для пауз используйте `tokio::time::sleep`.
- Для файловых операций используйте `tokio::fs` (если потребуется).

### 4.4. Доступ к БД и транзакции
- Не пишите «сырые» SQL-запросы напрямую в обработчиках диалогов или команд. Выносите всю логику работы с данными в соответствующие методы в `src/db/<domain>.rs`.
- Сложные связанные операции (например, публикация новой версии и привязка файлов) оборачивайте в транзакции `pool.begin().await?`.

## 🛠 5. Руководства по расширению функционала (How-To)

### 5.1. Как добавить новую команду бота
1. Откройте `src/handlers/mod.rs`:
   - Добавьте вариант в `enum Command` с атрибутом `#[command(description = "...")]`.
2. Если команда публичная:
   - Реализуйте функцию-обработчик в `src/handlers/commands_public.rs`.
   - Подключите вызов в `match cmd` в `src/handlers/mod.rs`.
3. Если команда администраторская:
   - Реализуйте функцию в `src/handlers/commands_admin.rs` (не забудьте проверить права через `db.admins().is_admin(user_id).await?`).
   - Подключите вызов в `match cmd` в `src/handlers/mod.rs`.
4. Обновите справочное сообщение в `/help` (`src/handlers/commands_public.rs`) при необходимости.

### 5.2. Как добавить новую инлайн-кнопку (Callback Query)
1. Выберите или создайте префикс данных callback (например, `myapp:<action>:<id>`).
2. В `src/handlers/callbacks/mod.rs` добавьте маршрутизацию по префиксу в `handle_callback`.
3. Реализуйте логику обработки в соответствующем модуле (`panel.rs`, `apk_moderation.rs`, `menu.rs` и т.д.).
4. Всегда подтверждайте обработку запроса вызовом `bot.answer_callback_query(q.id).await?` во избежание бесконечной загрузки индикатора на клиенте Telegram.

### 5.3. Как добавить новый шаг или ветку в FSM-диалог
1. В `src/dialogue/state.rs`:
   - Добавьте новое состояние в соответствующий enum (`SubmitApkState`, `EditApkState` или `AdminState`).
   - Убедитесь, что структуры имеют деривы `#[derive(Debug, Clone, Serialize, Deserialize)]`.
2. В соответствующем файле диалога (`src/dialogue/submit_apk.rs`, `src/dialogue/admin.rs` и т.д.):
   - Добавьте обработку входящего сообщения для нового состояния.
   - Вызовите `dialogue.update(NextState).await?` для перехода на следующий шаг.
   - Реализуйте обработку команд `/skip`, `/done` или `/cancel`, если шаг опционален.

### 5.4. Как изменить или расширить схему базы данных
1. В `src/db/mod.rs` внутри метода `Database::init_schema`:
   - Добавьте `CREATE TABLE IF NOT EXISTS ...` или идемпотентное добавление столбца.
2. Добавьте соответствующие методы и структуры моделей в репозитории `src/db/<repo>.rs`.
3. Добавьте экспорты в `src/db/mod.rs`.

## ⚠️ 7. Критические инварианты и запреты (Guardrails)

1. **Сохранность базы данных**:
   - Никогда не выполнять деструктивные команды `docker compose down -v` на боевом сервере (удалит volume `kostubet_data` с базой SQLite).
   - Все изменения схемы БД в `init_schema()` должны быть обратно совместимы и идемпотентны.
2. **Лимиты Telegram**:
   - Никогда не отправлять в Telegram API текст длиннее установленных ограничений (1024 для подписи к фото, 4096 для текста). Всегда использовать хелперы из `src/services/render.rs`.
3. **Безопасность FSM**:
   - Любое аварийное завершение диалога или необработанная ошибка должны очищать состояние или переводить пользователя в безопасное состояние (`Idle`), чтобы не блокировать последующие команды.
4. **Конфиденциальность и безопасность**:
   - Никогда не хардкодить токены ботов, GitHub токены, пароли или секреты в исходном коде. Все конфиденциальные данные считываются через `Config` (`.env` / переменные окружения).
